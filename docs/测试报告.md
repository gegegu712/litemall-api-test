## 一、测试概述

针对开源电商项目 litemall 的用户端接口开展功能测试，覆盖登录与鉴权、商品、订单三个模块，共设计并执行 24 条用例。测试分两轮进行：先用 Postman 逐条手工执行验证接口行为，再将验证过的场景固化为 pytest 自动化用例，接入 GitHub Actions 实现每次提交自动回归。

测试目标：

1. 验证用户端核心接口的功能正确性与参数校验逻辑
2. 验证订单状态机对非法操作的拦截能力——前端可以被绕过，后端必须拦住
3. 建立可重复执行的自动化回归能力，降低后续迭代的验证成本

## 四、测试方法与设计思路

| 方法 | 应用举例 |
| --- | --- |
| 等价类划分 | 订单状态划分为「可操作」与「不可操作」两类，各取代表值验证允许与禁止的操作 |
| 边界值分析 | 订单/商品列表分页参数取边界值：page=0、page=999、limit=1、limit=10000 |
| 状态迁移法 | 以订单状态机为基准，验证每个状态下允许与禁止的操作；对已取消订单逐一验证支付、取消、确认收货、退款均被拦截 |
| 对照法 | 同类接口横向对比：同样是"查询不存在的 ID"，订单详情返回业务错误码 720，商品详情返回 502 系统内部错误，由此定位缺陷 BUG-007 |
| 接口探测 | 缺少可信接口文档，先编写探测脚本批量请求候选场景、记录真实响应，再据此确定用例的预期值，避免"按想象写预期" |

补充说明：接口测试不能只依赖前端页面。前端的按钮置灰、提示拦截都只是界面层的约束，绕过前端直接调用接口才能验证后端是否真正做了校验——本次订单模块的用例全部采用直接调用接口的方式执行。

## 六、缺陷汇总

| 编号 | 缺陷描述 | 模块 | 严重程度 | 发现方式 |
| --- | --- | --- | --- | --- |
| bug002 | 注册页输入 10 位或 12 位手机号点击"下一步"无反应，无任何提示 | 注册 | 严重 | 页面功能测试 |
| bug003 | 忘记密码页"下一步"不校验手机号与验证码，直接跳转重置页 | 忘记密码 | 严重 | 页面功能测试 |

### 缺陷详情（接口测试发现）

**BUG-007：商品 ID 不存在时返回 502 系统内部错误**

- 复现步骤：调用 `GET /wx/goods/detail?id=99999999`
- 预期结果：返回表示"商品不存在"的业务错误码，与订单详情保持一致（订单详情查询不存在的订单返回 `720 订单不存在`）
- 实际结果：`{"errno": 502, "errmsg": "系统内部错误"}`
- 分析：502 表示服务端抛出了未被业务处理的异常，推测为查询结果为空后未做判空直接使用，属代码缺陷而非设计如此
- 状态：未修复（上游开源项目），已用 xfail 用例持续监控

**BUG-006：退款接口错误提示文案与操作不符**

- 复现步骤：对一条已取消订单调用 `POST /wx/order/refund`
- 预期结果：提示"订单不能申请退款"类文案
- 实际结果：`{"errno": 725, "errmsg": "订单不能取消"}`
- 分析：定位到 `WxOrderService.java` 中退款分支的错误文案与取消分支完全相同，属复制粘贴后漏改
- 状态：未修复（上游开源项目），已用 xfail 用例持续监控

## 七、遗留问题与风险

1. **支付链路完全没有验证**——这是本次测试最大的盲区。由于环境缺少微信商户配置，无法构造出已付款、待收货、已完成状态的订单，与之相关的所有状态流转均未验证。
2. **缺陷均为记录状态**——被测系统为开源项目，缺陷无法通过正规流程提交给开发方跟踪修复，仅做记录与用例监控。
3. **自动化用例数量仍偏少**（24 条），覆盖模块有限，尚未覆盖购物车、地址、售后等模块。
4. **接口鉴权只验证了订单接口**——其他模块接口是否同样做了登录态校验，未逐一验证。

## 八、测试结论

本次测试覆盖登录、鉴权、商品、订单共 24 条用例，执行通过 22 条、预期失败 2 条。核心接口的功能、参数校验与订单状态机拦截逻辑均工作正常，**未发现阻塞业务的严重缺陷**，接口层面具备基本可用性。

发现的 3 个接口缺陷中，BUG-007（系统内部错误）建议优先修复——它不仅影响用户体验，也说明商品查询链路存在未处理的空值分支；BUG-008、BUG-009 属规范性/安全性优化项，可排期处理。

**下一步建议**：① 在具备商户配置的环境中补充支付链路与订单全生命周期的验证；② 扩充自动化用例至 50 条以上，覆盖更多模块与异常场景；③ 将缺陷记录同步至缺陷管理工具，形成完整的缺陷生命周期闭环。
